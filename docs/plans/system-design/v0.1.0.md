# System Design — v0.1.0 Claude Plug-in

## 1. Overview

The Claude Plug-in is a locally-running Python MCP server (`claude-plug-in/mcp/`) paired with a set of Claude Code skill definitions (`claude-plug-in/skills/`). Together they give Claude access to InkClerk projects and documents on the user's machine, implementing the core UX contract inside the Claude environment:

> AI edits land as drafts → user reviews diff → user accepts → draft becomes the formal version.

The MCP server exposes the AI-callable half (tools, resources, prompts). The skill files expose the human-callable half (slash commands that orchestrate sequences of MCP tool calls with user prompts).

### 1.1 Supported Environments

| Environment | MCP Server | Skills |
|---|---|---|
| Claude Desktop App | ✓ | ✓ |
| Claude Code (CLI / IDE extension) | ✓ | ✓ |
| Claude Web App (claude.ai) | ✗ | ✗ |

Skills are exposed as **MCP Prompts** in the Desktop App; Claude Code receives them as namespaced slash commands defined in `skills/<name>/SKILL.md`.

The plug-in requires local filesystem access and is out of scope for the Claude Web App.

### 1.3 Transport and SDK

**Transport: stdio.** The MCP server is launched as a subprocess (`uv run python main.py`). The Claude client communicates with it over stdin/stdout using the MCP JSON-RPC protocol. No HTTP server is started.

**SDK style: FastMCP.** The official MCP Python SDK's `FastMCP` class is used throughout. Tools, resources, and prompts are registered via Python decorators (`@mcp.tool()`, `@mcp.resource()`, `@mcp.prompt()`). Modules are imported in `main.py` for their side effects (decorator registration).

**Grouping rationale:**
- `projects.py` and `documents.py` are CRUD tools over distinct entity types; `drafts.py` is the workflow layer; `import_google_doc.py` is a self-contained pipeline. Each file stays under ~200 lines.
- `resources.py` is one file because all four URI handlers share the same dispatch and utility calls.
- `shared/` has no MCP SDK imports — it is a pure utility layer usable by tools, resources, and prompts alike.
- `apps/web-api` is a separate deployable process from `claude-plug-in/mcp` — it runs on a public host (Render), not the user's machine, so the local MCP process (which has no public endpoint) can reach it. It never loads a Google client secret and never talks to Google at all; it's a secret-free relay for the browser → local-process handoff. Only `routers/import_session.py` exists in v0.1.0; `routers/projects.py`, `files.py`, `drafts.py`, `ai.py` are added in Milestone 3.

## 3. MCP Server Entry Point

### 3.1 `main.py`

```python
from mcp.server.fastmcp import FastMCP

mcp = FastMCP("inkclerk")

# Import tool modules for side effects (decorator registration)
import tools.projects          # noqa: F401
import tools.documents         # noqa: F401
import tools.drafts            # noqa: F401
import tools.import_google_doc # noqa: F401
import resources.resources     # noqa: F401
import prompts.prompts         # noqa: F401

if __name__ == "__main__":
    mcp.run()
```

Each tool module imports `mcp` from `main` (or from a shared module-level instance) and registers its tools at import time via `@mcp.tool()`. `mcp.run()` blocks on stdin, serving JSON-RPC requests.

### 3.2 `pyproject.toml`

```toml
[project]
name = "inkclerk-mcp"
version = "0.1.0"
requires-python = ">=3.11"
dependencies = [
    "mcp",
    "uuid7",
    "google-api-python-client",

The browser obtains the access token directly from Google via Google Identity Services; the MCP process only ever handles a bare access token, never a refresh token.

Start command: `cd claude-plug-in/mcp && uv run python main.py`

Intra-package imports use absolute style (the `mcp/` directory is on `sys.path` when running from there):

```python
from shared.fs import resolve_project, resolve_doc
from shared.errors import ProjectNotFoundError
```

## 4. Shared Utilities Design

### 4.1 `fs.py` — Filesystem Helpers

```python
PROJECTS_ROOT: Path = Path.home() / "Documents" / "InkClerk"
```

`PROJECTS_ROOT` is hard-coded as a module-level constant for v0.1.0. Future milestones may read it from a user config file; the constant name makes it easy to locate.

#### `slugify(name: str) -> str`

Derives a filesystem-safe folder name from a display name:
1. Lowercase the string.
2. Replace every run of whitespace and non-alphanumeric characters with a single hyphen.
3. Strip leading and trailing hyphens.

Non-ASCII letters (e.g. `é`, `中`) are treated as alphanumeric and preserved in project slugs. Example: `"Meeting Notes!"` → `"meeting-notes"`.

> Note: Google Doc import slugs use a stricter rule (non-ASCII stripped). `slugify` is not reused for that step; `import_google_doc.py` derives its own slug.

#### `resolve_project(name: str) -> tuple[Path, dict]`

Scans the immediate children of `PROJECTS_ROOT` (no recursive descent):
1. For each subdirectory, checks for `.inkclerk/project.json`.
2. Reads `project.json` and compares the `name` field to the argument (case-insensitive).
3. Returns `(project_path, project_json_dict)` on a unique match.
4. Raises `AmbiguousProjectNameError` if two or more projects match.
5. Raises `ProjectNotFoundError` if none match.

No result caching is performed. The scan is expected to be fast for the anticipated project count (<100 projects). `PROJECTS_ROOT` is scanned on every call.

#### `resolve_doc(project_path: Path, doc_path: str) -> Path`

1. Resolves `project_path / doc_path` to an absolute path.
2. Verifies the resolved path is still under `project_path` (prevents directory traversal via `..` components).
3. Raises `DocumentNotFoundError` if the path does not exist or is not a file.

#### `draft_path_for(project_path: Path, rel_path: str) -> Path`

Returns `project_path / ".inkclerk" / "drafts" / rel_path`. Does not check existence; callers check themselves.

#### `ensure_dir(path: Path) -> None`

Thin wrapper: `path.mkdir(parents=True, exist_ok=True)`.

---

### 4.2 `frontmatter.py` — YAML Frontmatter

#### `parse(text: str) -> tuple[dict, str]`

1. If `text` starts with `---\n`, reads lines until the next `---\n` (or `---` followed by EOF).
2. Parses the YAML block with `yaml.safe_load` (never `yaml.load`; prevents arbitrary code execution from a malformed file).
3. Returns `(meta_dict, body)` where `body` is the text after the closing delimiter, with a single leading newline stripped.
4. If no frontmatter block is present, returns `({}, text)`.
5. On malformed YAML, returns `({}, text)` and emits a warning rather than raising.

#### `write(meta: dict, body: str) -> str`

Serializes `meta` with `yaml.dump(default_flow_style=False, allow_unicode=True)` and returns:

```
---
{yaml block}---

{body}
```

`allow_unicode=True` ensures CJK characters in frontmatter values are written as raw Unicode, not escaped sequences.

#### Draft frontmatter rule

Draft files carry **no frontmatter**. A draft is pure Markdown body content. When `accept_draft` runs, it reads the formal file's existing frontmatter (`id`, `created`), combines it with the draft body, updates `lastModified` to the current UTC timestamp, and writes the merged result back to the formal file path.

### 4.3 `errors.py` — Structured Error Handling

```python
class InkClerkError(Exception):
    code: str = "INTERNAL_ERROR"

    def to_dict(self) -> dict:
        return {"error": self.code, "message": str(self)}


class ProjectNotFoundError(InkClerkError):
    code = "PROJECT_NOT_FOUND"

class AmbiguousProjectNameError(InkClerkError):
    code = "AMBIGUOUS_PROJECT_NAME"

class DocumentNotFoundError(InkClerkError):
    code = "FILE_NOT_FOUND"

class FileAlreadyExistsError(InkClerkError):
    code = "FILE_ALREADY_EXISTS"

class FolderAlreadyExistsError(InkClerkError):
    code = "FOLDER_ALREADY_EXISTS"

class NoDraftError(InkClerkError):
    code = "NO_DRAFT"

class AuthRequiredError(InkClerkError):
    code = "AUTH_REQUIRED"

class GoogleApiError(InkClerkError):
    code = "GOOGLE_API_ERROR"

class PermissionDeniedError(InkClerkError):
    code = "PERMISSION_DENIED"
```

Any Python exception that is not an `InkClerkError` (e.g. `PermissionError` from the OS, `json.JSONDecodeError`) is caught at the MCP layer, wrapped in a base `InkClerkError`, and returned as `INTERNAL_ERROR`.

## 5. Tool Implementation Pattern

Every tool in `tools/*.py` follows this skeleton:

```python
@mcp.tool(annotations={"readOnlyHint": True})  # annotation varies per tool
def read_document(project_name: str, doc_path: str) -> dict:
    # Step 1 — resolve project
    project_path, _ = resolve_project(project_name)
    # raises ProjectNotFoundError or AmbiguousProjectNameError

    # Step 2 — resolve document
    abs_path = resolve_doc(project_path, doc_path)
    # raises DocumentNotFoundError

    # Step 3 — perform operation
    text = abs_path.read_text(encoding="utf-8")
    meta, body = parse(text)

    # Step 4 — return result dict
    return {
        "content": body,
        "doc_id": meta.get("id"),
        "last_modified": meta.get("lastModified"),
        "has_draft": draft_path_for(project_path, doc_path).exists(),
    }
```

`list_projects` is the sole exception: it scans `PROJECTS_ROOT` directly without calling `resolve_project`.

### `rename_document` — assets reference rewrite

After renaming the `.md` file and any sibling assets folder (`{old_stem}-assets/` → `{new_filename}-assets/`), the tool must update any image references in the document body that point into the old assets folder. Implementation:

1. Read the document text (already on disk under the new name after step 2 of the behavior).
2. Call `frontmatter.parse` to separate `meta` and `body`.
3. Replace every occurrence of `./{old_stem}-assets/` in `body` with `./{new_filename}-assets/` (simple string replacement; no regex needed because the assets folder naming convention is deterministic).
4. Re-serialize with `frontmatter.write(meta, new_body)` and write back to the new path.

This step is skipped entirely if no assets folder was renamed (`assets_moved: false`).

### `move_document` — file move and assets relocation

`move_document` follows the same assets-rewrite pattern as `rename_document`, with two additional considerations:

- **Cross-device moves:** `Path.rename` fails when source and destination are on different filesystems. `move_document` uses `shutil.move` throughout to handle this transparently.
- **Cross-project draft relocation:** The draft is moved from `<src-project>/.inkclerk/drafts/<doc_path>` to `<dst-project>/.inkclerk/drafts/<destination_path>`. If the destination is the same project, this reduces to an intra-project draft move.

The assets-rewrite step is applied only when the assets folder was moved (`assets_moved: true`) and the document stem changed (old stem ≠ new stem derived from `destination_path`).

### Error interception

FastMCP wraps each tool call. Any `InkClerkError` raised inside a tool is caught, serialized with `.to_dict()`, and returned as a tool result with the MCP `isError: true` flag set. This keeps all tool functions free of error-formatting boilerplate.

Unhandled exceptions are caught by the same wrapper, logged, and returned as `{"error": "INTERNAL_ERROR", "message": "..."}` with `isError: true`.

### MCP annotations

| Annotation | Tools |
|---|---|
| `readOnlyHint: true` | `list_projects`, `read_document`, `list_documents`, `get_draft`, `get_diff` |
| `destructiveHint: true` | `delete_project`, `rename_project`, `delete_document`, `rename_document`, `accept_draft`, `reject_draft` |
| _(none)_ | `create_project`, `create_document`, `move_document`, `propose_edit`, `import_google_doc` |

## 6. Draft Storage Layout

The draft for a document mirrors the document's path relative to the project root, placed under `.inkclerk/drafts/`:

```
formal:  <project_root>/<rel_path>
draft:   <project_root>/.inkclerk/drafts/<rel_path>
```

Concrete example:

```
~/Documents/InkClerk/meeting-notes/
├── .inkclerk/
│   ├── project.json
│   └── drafts/
│       ├── 2026-06-kickoff.md       ← draft for meeting-notes/2026-06-kickoff.md
│       └── q3-planning/
│           └── roadmap.md           ← draft for meeting-notes/q3-planning/roadmap.md
├── 2026-06-kickoff.md               ← formal version (has frontmatter)
├── 2026-06-kickoff-assets/
│   └── diagram.png
└── q3-planning/
    └── roadmap.md                   ← formal version (has frontmatter)
```

Key rules:
- Draft files contain **no frontmatter** — body content only.
- The `.inkclerk/drafts/` subtree is created lazily by `propose_edit` via `ensure_dir`.
- Both `accept_draft` and `reject_draft` call `draft_file.unlink()` after their operations.
- `accept_draft` reads the original formal file's `id` and `created` fields and re-injects them (with updated `lastModified`) into the accepted content before writing.

## 7. Google Docs Import Pipeline

`import_google_doc` executes four sequential stages.

### 7.1 Stage 1 — Client-Side Google Sign-In and Document Pick

Neither Google's sign-in flow nor a public HTTPS redirect target is available to
`claude-plug-in/mcp` — it's a local stdio subprocess with no reachable endpoint, and Google's
client-side token model needs a browser anyway. Instead, the MCP process opens the system browser
to the hosted `apps/web` app's `/import/google-doc` page (§7.5), which obtains a `drive.file`
access token **directly from Google** using Google Identity Services
(`google.accounts.oauth2.initTokenClient`) — no client secret, no code exchange, entirely
client-side — and drives the Google Picker so the user picks the target document. Once both steps
complete, that page POSTs the result to the hosted `apps/web-api` relay (§7.5), which the MCP
process polls. `apps/web-api` never talks to Google and never holds a client secret; it only
relays `{access_token, expires_in, file_id, file_name}` from the browser to the local process.

Config: `INKCLERK_WEB_APP_URL` (opens the browser here) and `INKCLERK_WEB_API_URL` (polled for the
result) env vars on the MCP server, pointing at the deployed `apps/web` and `apps/web-api` Render
URLs respectively. Set via `claude-plug-in/.mcp.json`'s `env` block when launched through the
Claude Code plugin; must be set manually when running the MCP server any other way.

There is no local client-credentials file — `~/.config/inkclerk/google-oauth-client.json` is not
part of the design, and no access token is cached to disk either: `drive.file` only grants access
to the specific document picked through the Picker, and picking a document is how the caller
learns *which* document to import in the first place, so every call needs its own fresh
browser + Picker round regardless of whether a still-valid token exists. The Google OAuth client
ID and Picker API key are both meant to be public (embedded in the `apps/web` browser bundle); no
Google client secret exists anywhere in this system.

OAuth scope (requested client-side by the `apps/web` Picker page):
`https://www.googleapis.com/auth/drive.file`. Unlike `drive.readonly` (a *restricted* scope,
requiring Google's CASA security assessment and a demo video to verify), `drive.file` is a
*sensitive* scope: it only grants access to files the user explicitly selects through a Google
Picker (or files the app creates), never blanket read access to the user's whole Drive.

**No refresh token is ever issued** — this is inherent to Google Identity Services' client-side
token model (`initTokenClient`), not a limitation of this design. Since no token is cached, this
has no practical consequence: every call already runs the full flow below rather than refreshing
anything.

**Flow** (every call):

1. Generate `session_id = uuid4()`.
2. Open the system browser to `{WEB_APP_URL}/import/google-doc?session_id={session_id}`. The
   page there requests a token from Google (client-side) and drives the Picker; see §7.5.
3. Poll `GET {WEB_API_URL}/import/google-doc/session/{session_id}` every 2 seconds (timeout
   ~240s — long enough to cover Google's consent screen *and* picking a document in the Picker
   UI):
   - `{"status": "pending"}` → keep polling (covers both "not yet signed in" and "signed in,
     still choosing a document in the Picker").
   - `{"status": "ready", "access_token": ..., "expires_in": ..., "file_id": ..., "file_name": ...}` → build a `google.oauth2.credentials.Credentials(token=access_token)` and proceed to Stage 2 using `file_id`. The relay deletes the session entry once retrieved (single-claim).
   - Timeout or `{"status": "expired"}` → raise `AuthRequiredError`.

If `INKCLERK_WEB_APP_URL` or `INKCLERK_WEB_API_URL` is unset or unreachable at any point in this
flow, raise `AuthRequiredError` with a message pointing at the hosted sign-in flow.

Because the token just granted is always scoped to the file just picked, a 403 from the Drive API
in Stage 2 is treated as a real permission error (`PermissionDeniedError`), not something to retry
— there is no stale-token scenario to recover from.

### 7.2 Stage 2 — HTML Export via Drive API

```python
service = googleapiclient.discovery.build("drive", "v3", credentials=creds)
html_bytes = service.files().export(fileId=doc_id, mimeType="text/html").execute()
html = html_bytes.decode("utf-8")
```

Error handling:
- `HttpError` with status 403 → raise `PermissionDeniedError`.
- Any other `HttpError` → raise `GoogleApiError(f"Drive API error {status}: {reason}")`.

The Drive API HTML export is preferred over the Docs API JSON representation because it produces self-contained HTML suitable for direct conversion by `markdownify`.

### 7.3 Stage 3 — HTML → Markdown Conversion

**BeautifulSoup pre-processing pass** (before `markdownify`):

Parse the HTML with `BeautifulSoup(html, "html.parser")`. Collect all `<img src="...">` URLs during this pass for Stage 4. Do **not** strip or modify any `style` attributes — visual styles are preserved by the custom converter below.

**markdownify conversion:**

Use a custom `MarkdownConverter` subclass with two additional converters:

- `convert_span(el, text, convert_as_inline)`: If the `<span>` element's `style` attribute contains any of `color`, `background-color`, `font-family`, `font-size`, or `text-decoration`, emit `<span style="…">text</span>` verbatim (preserving only those properties; stripping any that are not in this set). Otherwise return `text` unchanged.
- `convert_u(el, text, convert_as_inline)`: Emit `<u>text</u>` verbatim, preserving underline applied via `<u>` elements.

```python
import markdownify

class InkClerkConverter(markdownify.MarkdownConverter):
    VISUAL_PROPS = {"color", "background-color", "font-family", "font-size", "text-decoration"}

    def convert_span(self, el, text, convert_as_inline):
        style = el.get("style", "")
        kept = [
            p.strip() for p in style.split(";")
            if p.strip() and p.strip().split(":")[0].strip() in self.VISUAL_PROPS
        ]
        if kept:
            return f'<span style="{"; ".join(kept)};">{text}</span>'
        return text

    def convert_u(self, el, text, convert_as_inline):
        return f"<u>{text}</u>"

md = InkClerkConverter(heading_style="atx", bullets="-").convert(html)
```

`heading_style="atx"` produces `#`-prefix headings (`# H1`, `## H2`, …) for all six levels. The alternative Setext style (`===` underlines) only supports two levels and is not used. `markdownify` defaults to Setext for H1/H2, so this argument is required.

`dropped_styles` always returns `[]`; no style tracking is needed.

**Unified diff note (`get_diff` tool):** `get_diff` uses Python's stdlib `difflib.unified_diff`, not `diff-match-patch`. `difflib.unified_diff` takes two lists of lines and directly produces the standard `+`/`-`/`@@` unified diff format suitable for display in a fenced `diff` code block. `diff-match-patch` is a character-level differ designed for operational transformation (it is what `packages/editor` uses for TipTap `DraftAddition`/`DraftDeletion` marks). It does not produce unified diff format natively and is the wrong tool for `get_diff`. `diff-match-patch` remains in `pyproject.toml` for the future editor integration.

### 7.4 Stage 4 — Image Download and Document Creation

**Image download:**

For each `<img>` URL collected in Stage 3:
1. Issue an authenticated GET request using `google.auth.transport.requests.AuthorizedSession(creds)`.
2. Derive the output filename from the URL's path component. Apply the 255-byte truncation rule (see §11.1).
3. Write raw bytes to `{project_path}/{subdirectory}/{output_slug}-assets/{image_filename}`.
4. Replace the `src` attribute in the converted Markdown with the `./`-prefixed, percent-encoded relative path.

**Output filename:**

If the `filename` argument is provided, use it directly. Otherwise, fetch the Google Doc title:

```python
meta = service.files().get(fileId=doc_id, fields="name").execute()
title = meta["name"]
```

Slugify the title for the output filename: lowercase, spaces → hyphens, non-ASCII characters stripped (unlike project slugs, which preserve non-ASCII).

**Document creation:**

Prepend InkClerk frontmatter to the converted Markdown body:

```markdown
---
id: <new uuid7>
created: <utc-iso8601 now>
lastModified: <utc-iso8601 now>
---

{converted markdown body}
```

Write to `{project_path}/{subdirectory}/{output_filename}.md`. If the file already exists, raise `FileAlreadyExistsError`.

Return `doc_path` and `doc_id`. `dropped_styles` is always `[]`.

### 7.5 Client-Side Picker (`apps/web`) and Import Relay (`apps/web-api`)

Two small hosted pieces replace the OAuth broker: an interactive page in `apps/web` that talks to
Google directly, and a secret-free relay in `apps/web-api` that hands the result to the local MCP
process. Neither ever loads a Google client secret.

**`apps/web`'s `/import/google-doc` page:** a client-side-only React route (not part of the
prerendered marketing pages). Reads `session_id` from the query string. On a "Sign in with Google"
button click (a user gesture is required to pop Google's consent window), calls
`google.accounts.oauth2.initTokenClient({client_id, scope: 'drive.file', callback}).requestAccessToken()`
— entirely client-side, via the Google Identity Services library
(`https://accounts.google.com/gsi/client`). Once the access token comes back, it loads the Picker
JS library (`https://apis.google.com/js/api.js`) and opens a `google.picker.PickerBuilder`
scoped to a Google Docs view (`setOAuthToken`, `setDeveloperKey`) — this is the step that actually
grants `drive.file` access to the specific document the user picks. Once a document is picked, the
page `POST`s `{access_token, expires_in, file_id, file_name}` to the `apps/web-api` relay below,
then tells the user they can return to their terminal.

**`apps/web-api`'s `routers/import_session.py`:** an in-memory session store (`session_id ->
{status, access_token, expires_in, file_id, file_name, created_at}`) is sufficient for v0.1.0 —
no database is introduced (Postgres arrives with the rest of `apps/web-api` in Milestone 3).
`status` moves straight to `"ready"` on `POST .../complete` (both sign-in and picking already
happened client-side by then), then to `"expired"` on first claim by `GET .../session/{id}`, or if
the TTL (10 minutes) elapses unclaimed. Because Render's free tier can recycle the process, an
in-progress import that outlives a restart simply requires the user to retry — acceptable for
v0.1.0.

**Endpoints:**

| Endpoint | Method | Behavior |
|---|---|---|
| `/import/google-doc/session/{session_id}/complete` | POST | Body `{"access_token": "...", "expires_in": ..., "file_id": "...", "file_name": "..."}`, called by the `apps/web` Picker page's own JS once the user signs in and picks a document. Stores the payload under `session_id`, status `"ready"`. |
| `/import/google-doc/session/{session_id}` | GET | Returns `{"status": "pending"}` if not yet completed, `{"status": "expired"}` if the TTL elapsed or it was already claimed, or the stored token + picked-file payload (and deletes the entry) if ready. |

**Config (env vars):**

| Variable | Purpose |
|---|---|
| `WEB_APP_ORIGIN` | The deployed `apps/web` origin, used to restrict CORS on `POST .../complete` (that request is cross-origin, from `apps/web`'s origin to this service) |

`apps/web` needs its own env vars (build-time, `VITE_`-prefixed, all meant to be public since
they're embedded in the browser bundle): `VITE_GOOGLE_CLIENT_ID`, `VITE_GOOGLE_PICKER_API_KEY`,
`VITE_WEB_API_URL` (this service's own deployed URL).

**Google Cloud setup (one-time, maintainer-only):**

1. Create a Google Cloud project → enable the Google Drive API and the Google Picker API.
2. Configure the OAuth consent screen (External). **Testing mode is sufficient to develop and exercise Task 6/7, but moving to Production for public marketplace distribution (Task 12) requires Google's verification** — a public Application home page and Application privacy policy link, plus an app logo. `drive.file` is a *sensitive* scope (unlike the *restricted* `drive.readonly` it replaces), so this verification does not require a CASA security assessment or a demo video. See Task 11, which stands up `apps/web`'s homepage/privacy/terms pages specifically to satisfy this and submits the consent screen for verification.
3. Create an OAuth client of type **Web application** under Credentials. Client secrets aren't used for this flow — only the client ID is needed, and it's meant to be public.
4. Add `apps/web`'s deployed origin (and a `localhost` dev origin) as authorized JavaScript origins. No redirect URI is needed — the Identity Services token client never redirects back through Google.
5. Create a separate API key for the Picker API, restricted by HTTP referrer to `apps/web`'s origin.
6. Store the resulting client ID and Picker API key as `apps/web`'s Render environment variables (`VITE_GOOGLE_CLIENT_ID`, `VITE_GOOGLE_PICKER_API_KEY`) — never in the repo. No secret exists to protect.

**Deployment (Render):**

- `apps/web-api/Dockerfile` builds the FastAPI relay; Render's web service points at this
  Dockerfile (or uses its native Python buildpack running
  `uvicorn main:app --app-dir src --host 0.0.0.0 --port $PORT`).
- `WEB_APP_ORIGIN` is set to `apps/web`'s deployed origin once known.
- A second Render service, a Static Site for `apps/web` (Task 11), is deployed from the same
  Render Blueprint (`render.yaml`) alongside `inkclerk-web-api`. Its deployed URL is what gets
  registered as the OAuth consent screen's Application home page / privacy policy links, and as
  `WEB_APP_ORIGIN` above.

## 8. Resource Handler Design

All four `inkclerk://` resources are handled in `resources/resources.py` via a single dispatcher registered with `@mcp.resource`:

```python
@mcp.resource("inkclerk://{+uri}")
def dispatch(uri: str) -> str:
    parsed = urllib.parse.urlparse(uri)
    params = {k: v[0] for k, v in urllib.parse.parse_qs(parsed.query).items()}
    match parsed.netloc:
        case "projects":
            return json.dumps(_list_projects())
        case "project":
            return json.dumps(_get_project(params["name"]))
        case "document":
            return json.dumps(_get_document(params["project"], params["path"]))
        case "draft":
            return json.dumps(_get_draft(params["project"], params["path"]))
        case _:
            raise ValueError(f"Unknown resource URI: {uri}")
```

All resource responses are serialized as JSON. MIME type: `application/json`.

URI dispatch table:

| URI | Required params | Handler |
|---|---|---|
| `inkclerk://projects` | none | Returns same schema as `list_projects` |
| `inkclerk://project?name=…` | `name` | Returns project metadata + document list |
| `inkclerk://document?project=…&path=…` | `project`, `path` | Returns formal document content (frontmatter stripped) |
| `inkclerk://draft?project=…&path=…` | `project`, `path` | Returns current draft content |

Each `_handler` function calls `resolve_project` / `resolve_doc` / `frontmatter.parse` directly from `shared/`. No logic is duplicated from the tools layer.

If a handler raises an `InkClerkError`, the dispatcher catches it and returns `json.dumps(error.to_dict())`.

## 9. Skill Definitions

Skill files are `SKILL.md` files in `claude-plug-in/skills/<name>/` subdirectories. They are loaded by the Claude Code Plugin system and define namespaced slash commands. Each file has a YAML frontmatter header followed by a Markdown instruction body.

Skills have no Python environment and no `pyproject.toml`. A `SKILL.md` file is read-only prose that Claude interprets at runtime; it never executes code itself. Any computation a skill needs is performed by an MCP tool in `claude-plug-in/mcp/`. If a future skill required a standalone helper script, the preferred path is to expose that logic as an MCP tool rather than adding a second Python environment.

Each Claude Code skill has a 1:1 MCP Prompt counterpart (registered in `prompts/prompts.py`) that delivers the same workflow to Claude Desktop App users. The skill file defines the slash command; the MCP Prompt defines the Desktop App entry point.

| Claude Code skill | MCP Prompt |
|---|---|
| `/inkclerk:import-google-doc` | `import_google_doc` |
| `/inkclerk:propose-edit` | `edit_document` |
| `/inkclerk:accept-draft` | `accept_draft` |
| `/inkclerk:reject-draft` | _(none — `reject_draft` tool only)_ |

### 9.1 Frontmatter Fields

| Field | Description |
|---|---|
| `description` | Shown in `/help` and the command picker |
| `argument-hint` | Optional human-readable argument signature |

The skill invocation name is derived from the directory name, not from a frontmatter field. A skill in `skills/import-google-doc/SKILL.md` inside a plugin named `inkclerk` is invoked as `/inkclerk:import-google-doc`.

### 9.2 `/inkclerk:import-google-doc` (`import-google-doc/SKILL.md`)

_Desktop App equivalent: `import_google_doc` MCP Prompt._

```yaml
---
description: Import a Google Doc into an InkClerk project as a Markdown document
argument-hint: "[project-name] [filename]"
---
```

Instruction body follows requirements §4.1 flow:
1. Parse `$ARGUMENTS` for optional positional args (project name, filename). There is no URL/ID argument — the tool always opens the browser Picker for the user to choose the document.
2. Prompt for any missing required args (project name).
3. Call `import_google_doc`.
4. Report the created document path.

### 9.3 `/inkclerk:propose-edit` (`propose-edit/SKILL.md`)

_Desktop App equivalent: `edit_document` MCP Prompt._

```yaml
---
description: Propose an AI-generated edit to a document and write it as a draft
argument-hint: "[instruction]"
---
```

Instruction body follows requirements §4.2 flow:
1. Identify target document (current open file, or prompt for path).
2. Call `read_document` to fetch content.
3. Ask for editing instruction if not provided in `$ARGUMENTS`.
4. Generate revised Markdown body.
5. Call `propose_edit`. If `overwritten: true`, surface: "A previous draft was replaced."
6. Call `get_diff` and display the result in a fenced `diff` code block.
7. Prompt: "Run `/inkclerk:accept-draft` to accept or `/inkclerk:reject-draft` to discard."

### 9.4 `/inkclerk:accept-draft` (`accept-draft/SKILL.md`)

_Desktop App equivalent: `accept_draft` MCP Prompt._

```yaml
---
description: Accept the pending draft, making it the formal version of the document
argument-hint: "[doc-path]"
---
```

Instruction body follows requirements §4.3 flow:
1. Identify target document (current open file, or prompt for path).
2. Call `get_diff` and display the diff for final review.
3. Ask: "Accept this draft? This will overwrite the formal document. (yes/no)"
4. If yes: call `accept_draft`, report "Draft accepted. The formal document has been updated."
5. If no: report "Cancelled. The draft was not accepted."

### 9.5 `/inkclerk:reject-draft` (`reject-draft/SKILL.md`)

_Desktop App equivalent: `reject_draft` MCP tool (no dedicated Prompt)._

```yaml
---
description: Discard the pending draft without modifying the formal document
argument-hint: "[doc-path]"
---
```

Instruction body follows requirements §4.4 flow:
1. Identify target document (current open file, or prompt for path).
2. Call `get_draft` to confirm a draft exists and display what will be discarded.
3. Ask: "Discard this draft? The formal document will remain unchanged. (yes/no)"
4. If yes: call `reject_draft`, report "Draft discarded. The formal document was not changed."
5. If no: report "Cancelled. The draft was not discarded."

## 10. Error Handling

### 10.1 Structured Error Payload

All tool errors return:

```json
{ "error": "<CODE>", "message": "human-readable description" }
```

### 10.2 Error Code Table

| Code | Exception class | Raised by |
|---|---|---|
| `PROJECT_NOT_FOUND` | `ProjectNotFoundError` | All tools that accept `project_name`, except `list_projects` and `create_project` |
| `AMBIGUOUS_PROJECT_NAME` | `AmbiguousProjectNameError` | Same set as above |
| `FILE_NOT_FOUND` | `DocumentNotFoundError` | `read_document`, `delete_document`, `rename_document`, `move_document`, `propose_edit`, `get_draft`, `get_diff`, `accept_draft`, `reject_draft` |
| `FILE_ALREADY_EXISTS` | `FileAlreadyExistsError` | `create_document`, `rename_document`, `move_document`, `import_google_doc` |
| `FOLDER_ALREADY_EXISTS` | `FolderAlreadyExistsError` | `create_project`, `rename_project` |
| `NO_DRAFT` | `NoDraftError` | `get_draft`, `get_diff`, `accept_draft`, `reject_draft` |
| `AUTH_REQUIRED` | `AuthRequiredError` | `import_google_doc` |
| `GOOGLE_API_ERROR` | `GoogleApiError` | `import_google_doc` |
| `PERMISSION_DENIED` | `PermissionDeniedError` | `import_google_doc` |
| `INTERNAL_ERROR` | `InkClerkError` (base) | Any tool, on unexpected exception |

### 10.3 Exception Propagation

```
tool function body
  → raises InkClerkError subclass
    → FastMCP tool wrapper catches InkClerkError
      → calls error.to_dict()
        → returns {"error": ..., "message": ...} as tool result content
          with isError: true in the MCP response
```

Tool errors use the MCP `isError: true` flag so that Claude can semantically distinguish a business-logic failure from a successful result. This is distinct from a protocol-level MCP error (e.g., unknown method), which the SDK handles separately.

## 11. Non-functional Design

### 11.1 Unicode and CJK Filename Handling

Three rules apply throughout all file I/O:

1. **On disk — raw Unicode.** All `Path.read_text` / `Path.write_text` calls use `encoding="utf-8"`. Filenames and folder names are stored as raw Unicode (e.g. `會議記錄.md` on disk).

2. **In Markdown references — percent-encoded.** When writing image paths or cross-references into `.md` files, apply `urllib.parse.quote(path_component, safe="")` to any path segment that may contain non-ASCII characters. Example:

   ```markdown
   ![圖片](./%E6%9C%83%E8%AD%B0%E8%A8%98%E9%8C%84-assets/%E5%9C%96%E7%89%87.png)
   ```

3. **Filename length — 255-byte limit.** The filesystem limit applies to bytes, not characters.

   | Character type | Bytes per char | Max chars in 255-byte name |
   |---|---|---|
   | ASCII | 1 | 255 |
   | CJK (most common) | 3 | ~85 |
   | Emoji (4-byte) | 4 | ~63 |

   The truncation helper in `fs.py` encodes the candidate basename to UTF-8, truncates the byte string to leave room for the `.md` extension (251 bytes max for the stem), then decodes back to a string dropping any incomplete UTF-8 sequence at the tail.

### 11.2 Python Version and Tooling

- Python `>=3.11` required. The `match` statement (3.10+) is used in the resource dispatcher.
- `uv` is the sole package manager. No `pip`, `requirements.txt`, or `setup.py`.
- `uv run python main.py` auto-creates the virtualenv and installs dependencies on first run.
- No `__main__.py`; `main.py` is invoked directly as `python main.py` from the `mcp/` directory. All intra-package imports use the `shared.*`, `tools.*`, etc. style.
